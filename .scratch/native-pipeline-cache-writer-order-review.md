# Native pipeline cache-writer ordering

Source-only audit of frozen V17 (060ec3a13); no behavior changes or new measurements.

The immediate-edit regression has a concrete scheduling explanation in the source. `finishPreparedNative` first completes `Semantic.finishBuildArtifact`, including accepted dependency import and retained-worker shutdown. It then calls `NativeCoordinator.publish`, whose first operation waits/reaps the native child. Only after that child is done does the helper return to `build`; main then calls `SemanticCache.storePacks`, followed by `saveDetached`. The semantic cache writer therefore cannot overlap the remaining native child tail. Ordinary builds start that writer before their native compilation, which often hides the writer's work before the user can launch an edit.

The earliest safe writer start is after successful finishBuildArtifact and the helper's existing import/syntax/missed-source validation, before publish/wait. At that point the retained proof, selected MIR/emission evidence and final assembled preview are authoritative; the parent still has a single thread. The native coordinator is a separate process, and finishBuildArtifact has already closed/reaped semantic workers. Forking a cache writer then does not require publishing private native objects or waiting for native success: semantic/native-text cache evidence is valid independently of whether Clang or the final link later succeeds, matching ordinary build behavior.

A narrow implementation can extract the existing main cache checkpoint (storePacks + saveDetached) into one driver function. finishPreparedNative invokes it at that safe point and returns a driver-owned `cacheSaved` result; main skips the same checkpoint when it already ran. Unsupported, nondeferred, refused or serial-retry paths continue to the ordinary checkpoint. Avoid putting persistence policy into Semantic.ArtifactCompletion. Cleanup must still wait/remove the native staging directory on every error, including an allocation failure after writer handoff. The writer must not run parent cleanup/destructors; existing DetachedWriter.finish exits directly.

Moving pack writing alone is sound for native input ownership but does not solve the late-start barrier. `storePacks` does not modify Semantic or CodegenUnit bodies; it only writes content-addressed bodies. The native child and parent compile from owned unit/pack bytes, not these newly written files. The cache child can write packs before its manifest/image publication. Preserve these ordering rules: create the pack directory in the parent before forking, do not recreate it in the child after a concurrent clean, keep pack writes inside the cache writer's lock, publish the image only after its needed pack writes, prune only after publication. Missing pack I/O already causes conservative native replay misses; it must not be treated as a successful held pack.

An explicit writer-settlement policy is the simpler alternative if honest completion and immediate edit latency matter more than detached foreground return. Current DetachedWriter.Handoff.Original discards the writer PID, so settling only this command's writer requires returning a token/PID and waiting it (with EINTR handling), not waiting all children or acquiring an unrelated cache lock. Cleanup must settle it on errors too. Waiting immediately after handoff would destroy existing overlap; wait at the command's completion boundary after native/link work. This would expose the already measured settled wall time, not create a new speedup.

Before choosing policy, use same-binary immediate off/on controls after the CPU0 lane as requested. Record writer handoff, native coordinator done, native/link done, writer done and next-edit launch/finish. Then a candidate early-checkpoint treatment can test whether it hides the writer tail without increasing total CPU/PSS or moving still more work into the edit. Required correctness gates: native child failure still seeds valid semantic evidence; proof failure never checkpoints the rejected preview; writer failure/clean does not recreate cache directories; all child FDs/reaping remain correct; fresh first edit consumes the completed cache with exact diagnostics/output. No performance benefit is inferred from source ordering alone.
