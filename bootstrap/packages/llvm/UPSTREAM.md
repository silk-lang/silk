## Compatibility baseline

The authoritative interoperability baseline is LLVM `22.1.8`. The complete fixture corpus is
assembled with `llvm-as`, disassembled with `llvm-dis`, verified with `opt -passes=verify`, and
inspected with `llvm-bcanalyzer`. The published runtime supports Node.js `>=22.13.0` and does not
load Zig, LLVM, or platform executables. Other LLVM 22 patch releases are expected to be compatible
but are informational until explicitly promoted in the parity manifest.

## Known deviations

- Zig allocator, pointer, `AssumeCapacity`, deinitialization, and mutable WIP APIs are represented
  by builder-owned immutable handles, scoped Effect transactions, and one serialized mutation gate.
- Operations are grouped into actor modules instead of mirroring every Zig method name. Settings
  use closed value actors and sibling functions; constants and local values share typed input
  boundaries where Zig uses a packed union.
- JavaScript `number` is accepted only for safe bounded integers. Arbitrary-width LLVM values,
  lengths, and exact bit patterns use `bigint` or `ByteString`.
- `dump` and filesystem-print conveniences are omitted from the runtime core. `IrText.render`
  returns a string and `Bitcode.encode` returns `Uint8Array`; applications choose their Effect
  platform filesystem boundary.
- Alignment forward references are not public. Alignment is validated before an instruction is
  committed; metadata and SSA forward references retain their supported explicit lifecycles.
- Exact Zig bytes are required only for the declared exact fixture class. Larger modules may choose
  different legal abbreviation and ordering strategies and are compared as canonical LLVM text,
  analyzer structure, and verifier-accepted semantics.
- `ir.zig` contains legacy and general LLVM schema vocabulary that the pinned builder never emits.
  Those records remain inventoried but are not exposed or approximated by the public API.

## Upstream unsupported paths

The mechanically extracted inventory records every pinned `TODO`, `unreachable`, explicit panic,
and panic-only assertion path. These entries receive the `upstream-unsupported` disposition in the
parity manifest and are not claimed as implemented behavior. Recoverable malformed public input in
the Effect port fails with `LlvmError`; internal corruption remains a defect. The authoritative
entry list is [parity/upstream-inventory.json](./parity/upstream-inventory.json), and its validated
summary is [parity/REPORT.md](./parity/REPORT.md).

## Reviewing an upstream candidate

Run the candidate workflow with an explicit commit:

```sh
pnpm --filter @silklang/llvm upstream:candidate -- <zig-commit>
```

The command downloads only the selected three sources, prints their hashes, extracts a candidate
inventory, and reports added and removed construct IDs against the committed baseline. It never
changes the baseline, application source, or parity manifest. Add `--regenerate-fixtures` only when
you intentionally want to rebuild current development fixtures. Adoption requires a reviewed
OpenSpec change, hash updates, disposition review for every inventory diff, the pinned Zig oracle
where exact bytes apply, and the complete parity and release gates.
